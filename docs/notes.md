# Notes on Ampersand

## Known Edge Cases Not Handled
 + gnome-terminal. It runs new tabs from a long-lived server process, so stale SBOX_* variables in that server's environment could still reach the launch. That would only happen if the server itself was started from a shell Ampersand launched. I left it alone.

## sbox-cli unavailable in Preferences > AI Agents after opening a project from the sbox launcher (investigated, not fixed)

Repro path
 - Ampersand GUI -> sbox-dev with no -project -> hub sbox-launcher -> pick a project -> hub spawns the editor -> Preferences > AI Agents shows "Couldn't run sbox-cli. See the console for details."
 - That text is AgentSkillRows.cs:31, shown exactly when AgentSkill.Status() returns null (AgentSkillRows.cs:29). Status() returns null when Run("--skill-status") is not ExitCode 0 (AgentSkill.cs:39); Run is null on exception (logged, AgentSkill.cs:76) or a 10s timeout, and a non-zero exit is a Result, so it is NOT logged. Grep of every game/logs/*.log found no "Agent skill", "sbox-cli" or "couldn't run" line at all -> it failed without throwing. INFERRED (from the bwrap test below): the apphost started and exited non-zero.

Root cause - the sbox-cli apphost cannot find a .NET runtime in the Steam Linux Runtime 4.0 container. VERIFIED, reproduced.
 - AgentSkill.Cli is Environment.CurrentDirectory + bin/managed/sbox-cli (AgentSkill.cs:22). The path is right, so the cwd theory is out: the hub starts the editor with WorkingDirectory = Environment.CurrentDirectory (LauncherWindow.cs:938), that cwd is game/ (readlink /proc/77434/cwd on the live hub), the engine then chdirs to the engine folder itself (NetCore.cs:38 InitializeInterop(Environment.CurrentDirectory), AppSystem.cs:52), and game/bin/managed/sbox-cli exists and is executable (-rwxr-xr-x).
 - The binary is fine on the host: `SBOX/game/bin/managed/sbox-cli --skill-status` exits 0 with the expected JSON, and still exits 0 with the editor's LD_PRELOAD/LD_LIBRARY_PATH exported, so the HarfBuzz/casefold preload is not the cause. VERIFIED.
 - The container has no .NET anywhere: SteamLinuxRuntime_4/steamrt4_platform_4.0.20260928.262390/files has no usr/bin/dotnet, no usr/lib/dotnet, no usr/share/dotnet and no etc/dotnet. VERIFIED.
 - The hub's environment has no DOTNET_ROOT and PATH=/usr/bin:/bin (read-only /proc/77434/environ); the engine's own runtime sits in game/bin/dotnet (StageLinuxRuntime, BuildManaged.cs:150-157). VERIFIED.
 - Reproduced on the host by hiding the host's only pointer (etc/dotnet/install_location -> /usr/lib/dotnet): `bwrap --dev-bind / / --tmpfs /etc/dotnet --chdir game -- ./bin/managed/sbox-cli --skill-status` prints "You must install .NET to run this application. ... .NET location: Not found / searched: Application directory, DOTNET_ROOT = <not set>, /etc/dotnet/install_location_x64 = <not set>, /usr/share/dotnet" and exits 131. VERIFIED.
 - Why the other launchers survive the same container: sbox-dev and sbox-launcher are built with `-p:AppHostRelativeDotNet=bin/dotnet` (BuildManaged.cs:96, comment at :89-95) so their apphosts carry an embedded relative runtime path next to themselves; `strings game/sbox-dev` and `strings game/sbox-launcher` contain "bin/dotnet", `strings game/bin/managed/sbox-cli` does not. sbox-cli is built through engine/Sandbox-Engine.slnx:23 by BuildManaged Step 5, which never passes that property, and Sbox-Cli.csproj does not set it either. VERIFIED.
 - Consequence (VERIFIED): any editor running inside the Steam runtime fails this way, not only one opened from the hub picker. An editor started directly with `ampersand --launch sbox-dev --project P` (no picker) ran `bin/managed/sbox-cli --skill-status` from inside the editor with the same result: exit 131, ".NET location: Not found". A host-side run (runtime off) works because the host does have dotnet.
 - Second layer, VERIFIED: with the runtime found (DOTNET_ROOT set), sbox-cli still aborts inside the container (exit 134, "Couldn't find a valid ICU package installed on the system"), because the container has no ICU either. The engine's launchers carry System.Globalization.AppLocalIcu=72.1.0.3 (engine/Launcher/Directory.Build.targets, linux-x64 RuntimeIdentifier only) and load the ICU that StageLinuxRuntime puts beside CoreCLR in game/bin/dotnet/shared/Microsoft.NETCore.App/<ver>/. sbox-cli is built without a RuntimeIdentifier, so it gets neither that option nor the bin/dotnet hint.

Candidate fixes
 - A. Engine fork, build (smallest, follows the launcher precedent): give the sbox-cli apphost a relative dotnet root. The value must be relative to the apphost's own directory, so a binary in game/bin/managed needs "../dotnet" ("bin/dotnet" only works for the copies in game/, which is why the existing four launchers use it). Add the property in Sbox-Cli.csproj (Linux-conditioned) or in whichever command builds it. It needs both pieces: the relative dotnet root AND the AppLocalIcu option; building sbox-cli with -r linux-x64 like the launchers would give it the Directory.Build.targets option. Trade-off: hard-codes where sbox-cli is installed; correct value can be proven with the bwrap check below.
 - B. Engine, code: in AgentSkill, resolve the engine folder instead of trusting Environment.CurrentDirectory (FACEPUNCH_ENGINE or AppContext.BaseDirectory) and pass DOTNET_ROOT=<engine>/bin/dotnet in ProcessStartInfo.Environment. The spawned sbox-cli also needs DOTNET_SYSTEM_GLOBALIZATION_APPLOCALICU=72.1.0.3 (or the version found next to CoreCLR). Trade-off: fixes the editor's own calls only; sbox-cli invoked from an agent shell or MCP config still needs fix A, and the cwd dependence at AgentSkill.cs:22 is worth removing on its own.
 - C. Ampersand: export DOTNET_ROOT=$GAME_DIR/bin/dotnet in apps/_common.sh and add DOTNET_ROOT to the --env allowlist in SteamRt4Runtime so it crosses the container boundary (only allowlisted vars cross). The spawned sbox-cli also needs DOTNET_SYSTEM_GLOBALIZATION_APPLOCALICU=72.1.0.3 (or the version found next to CoreCLR), so that too must cross the boundary. Trade-off: it is the one fix that also covers non-ampersand consumers of sbox-cli, but it edits ampersand's contract with the engine, it can hide fix A, and it does not help anyone who starts the hub outside ampersand.
 - Separately worth noting: Run() logs only on exception (AgentSkill.cs:76), so the apphost's own ".NET not found" message was swallowed. Logging result.Message on a non-zero exit would have made this diagnosable from game/logs.

How to verify a fix
 1. Host-side gate, no s&box process involved: `bwrap --dev-bind / / --tmpfs /etc/dotnet --chdir game -- ./bin/managed/sbox-cli --skill-status` must print the two-target JSON and exit 0 (today: "You must install .NET", exit 131).
 2. Check the hint landed: `strings game/bin/managed/sbox-cli | grep dotnet` should now show a hint, as it already does for sbox-dev.
 3. Real path: launch the hub from Ampersand with the Steam runtime on, open a project, and Preferences > AI Agents should list the Claude/Codex rows instead of "Couldn't run sbox-cli".
